## Overview

```bash
hush <command> [options]
```

Hush keeps secrets **encrypted at rest**. The primary way to use secrets is `hush run -- <command>`, which decrypts to memory and injects environment variables—secrets never touch the disk.

### Command Categories

| Category | Commands | Description |
|----------|----------|-------------|
| **Primary (AI-Safe)** | `run`, `materialize`, `set`, `copy-key`, `move-key`, `edit`, `inspect`, `has` | Safe command surfaces that avoid printing secret values |
| **Setup** | `bootstrap`, `config`, `init`, `migrate`, `encrypt`, `status`, `doctor`, `skill` | Repository setup, diagnostics, and bounded migration, with `encrypt` kept only as a retired legacy bridge |
| **Topology** | `file`, `bundle`, `target` | Manage the files, bundles, and targets that define what secrets go where |
| **Deployment** | `push`, `project`, `check` | CI/CD, runtime secret sync, and cloud deployment |
| **Debugging** | `resolve`, `trace`, `verify-target`, `diff`, `export-example` | Debug safe output, provenance, target completeness, and example generation |

### Global Options

| Option | Description |
|--------|-------------|
| `-e, --env <env>` | Environment: `development` or `production` (default: `development`) |
| `-r, --root <dir>` | Start directory for project mode, execution directory for `run` |
| `--global` | Use the explicit global store at `~/.hush` |
| `-h, --help` | Show help message |
| `-v, --version` | Show version number |

Every command supports repository-free command help: `hush <command> --help`. Command help lists only options accepted by that command, including known value domains and safe alternatives; it does not decrypt files or contact providers.

### Update check

Hush checks for new versions once per day via a standard HTTP request to the npm registry. No telemetry is sent. To disable, set `HUSH_NO_UPDATE_CHECK=1` (also respects `NO_UPDATE_NOTIFIER=1` and any `CI` environment variable).

## run

Run a command with secrets injected as environment variables. **This is the primary way to use secrets.** Secrets are decrypted to memory only—they never touch the disk.

```bash
# Run with development secrets (default)
hush run -- npm start

# Run with a specific v3 target
hush run -t api -- wrangler dev
hush run --target web -- npm start

# Run with global secrets only
hush run --global -- npm start
```

### Options

| Option | Description |
|--------|-------------|
| `-t, --target <name>` | Resolve a specific v3 target; otherwise Hush uses `runtime` or the only non-example target |
| `-- <command>` | The command to run (everything after `--`) |

<Aside type="caution">
`-e/--env` is not a valid flag for `hush run` and will produce an error. Use `--target` to select a named v3 target instead (e.g. `hush run --target prod -- npm build`).
</Aside>

### How It Works

1. Loads the v3 repository from `.hush/`
2. Resolves the selected target through the shared resolver/materializer
3. Decrypts to memory only and emits audit events
4. Spawns the child process with the resolved environment
5. Cleans up any staged runtime state automatically on failure or signals

When `--global` is used, Hush reads only from `~/.hush`. It does not merge project secrets.

### Examples

```bash
# Local development
hush run -- npm run dev

# Wrangler with API secrets only
hush run -t api -- wrangler dev

# Docker with secrets
hush run -- docker compose up

# Any command that needs secrets
hush run -- node scripts/migrate.js
```

<Aside type="tip">
Use `-t` to choose a specific v3 target when the repo declares more than one runtime target.
</Aside>

## materialize

Write a v3 target or bundle to explicit file paths for CI, native build tooling, or other file-based consumers.

This command uses the existing v3 resolver/materializer, but unlike `hush run` it **persists** the resulting plaintext files under a chosen output root so later steps can import them into keychains, provisioning-profile directories, or other tools.

```bash
# Materialize a target to an explicit output root
hush materialize -t ios-signing --json --to /tmp/fitbot-signing

# Materialize for the lifetime of one command, then auto-clean
hush materialize -t ios-signing --to /tmp/fitbot-signing -- bash scripts/ci/install-ios-signing.sh /tmp/fitbot-signing

# Materialize a bundle directly
hush materialize --bundle fitbot-signing --to /tmp/fitbot-signing

# Clean up a previously materialized output root
hush materialize --cleanup --to /tmp/fitbot-signing
```

### Options

| Option | Description |
|--------|-------------|
| `-t, --target <name>` | Resolve a specific v3 target; otherwise Hush uses `runtime` or the only non-example target |
| `--bundle <name>` | Materialize a bundle directly instead of selecting a target |
| `--json` | Emit machine-readable JSON describing written paths and cleanup hints |
| `--format <dotenv>` | Render env output in dotenv format (default) |
| `--output-root <dir>` / `--to <dir>` | Output root for persisted plaintext artifacts (default: `.hush-materialized/`) |
| `--cleanup` | Remove the materialized output root instead of writing files |
| `-- <command>` | Run a child command with the materialized files available, then auto-clean the output root when it exits |

### Artifact path metadata

Artifact entries can control where they land under the chosen output root:

- `filename` — override the final filename
- `subpath` — override the output directory under the root
- `materializeAs` — override the full relative output path

Targets can also declare the same metadata for the target artifact itself.

### How It Works

1. Loads the v3 repository and resolves the selected target or bundle
2. Materializes file and binary artifacts using the shared runtime pipeline in persisted mode
3. Writes files under the chosen output root with restrictive permissions
4. If a child command is provided after `--`, runs that command with the resolved env plus `HUSH_MATERIALIZE_OUTPUT_ROOT` available and auto-cleans on exit
5. Otherwise emits an audit event and returns only metadata/path information to stdout
6. Leaves manual cleanup available via `hush materialize --cleanup` when you intentionally need a longer-lived output root

### JSON output shape

`--json` returns metadata only — never raw secret contents. It includes full metadata like `repositoryRoot`, `files`, `logicalPaths`, hashes, and path details. This makes it suitable for CI pipelines that need a stable handoff surface without logging private values.

### Auto-cleaning command flow

When you append a command after `--`, Hush treats the materialized files as ephemeral job-scoped state:

```bash
hush materialize -t ios-signing --to /tmp/fitbot-signing -- bash scripts/ci/install-ios-signing.sh /tmp/fitbot-signing
```

In that mode Hush:

1. writes the files under the chosen output root
2. runs the child command
3. deletes the materialized output root afterwards, even if the command fails

Use this mode for signing, certificates, provisioning profiles, or other native-tooling flows that only need the files for one step.

<Aside type="tip">
Use `hush materialize -- <command>` as the default for maintained file-based workflows like Apple signing, certificates, provisioning profiles, or other binary artifacts. Keep using plain `hush materialize --json` when another tool needs path metadata, and keep using `hush run` whenever a process can consume values from memory only.
</Aside>

## import add

Bind a bundle or file from another Hush repository.

```bash
hush import add --source-root /absolute/path/to/source --bundle shared-runtime
hush import add --source-root /absolute/path/to/source --file env/project/shared --import-name shared-config
```

The absolute source root is persisted inside the encrypted destination manifest. Commands that resolve the import require the source repository and its age key to be available locally. Use `--import-name` to set a stable local name; otherwise Hush derives one from the source.

| Option | Description |
|--------|-------------|
| `--source-root <path>` | Absolute or resolvable path to the source Hush repository |
| `--bundle <name>` | Import one source bundle |
| `--file <path>` | Import one source file |
| `--import-name <name>` | Override the derived local import name |
| `--json` | Emit machine-readable output |

## set

Set a secret. Supports inline values, interactive prompts, or piped input.

```bash
# Inline value (recommended for AI agents)
hush set DATABASE_URL "postgres://user:pass@host/db"
hush set STRIPE_KEY "sk_live_xxx" -e production
hush set ELEVENLABS_API_KEY "$ELEVENLABS_API_KEY" --global
hush set FEATURE_FLAG "enabled" --local

# Write to a specific repository file using --file
hush set DATABASE_URL "postgres://user:pass@host/db" --file env/project/staging
hush set API_KEY "sk_test_xxx" --file production

# Write to the machine-local override store
hush set DATABASE_URL "postgres://user:pass@host/db" --repo-local
hush set DATABASE_URL "postgres://user:pass@host/db" --file local
hush set DATABASE_URL "postgres://user:pass@host/db" --file user/local

# Interactive prompt (for users)
hush set DATABASE_URL
hush set API_KEY -e production

# Set in machine-local overrides
hush set MY_OVERRIDE --local

# Set in the explicit global store
hush set --global OPENAI_API_KEY

# Bootstrap the global store without a separate init step
hush keys generate --global
hush set --global OPENAI_API_KEY

# Piped input (for scripts/automation)
echo "my-secret" | hush set MY_KEY
cat cert.pem | hush set CERTIFICATE
```

### Options

| Option | Description |
|--------|-------------|
| `-e, --env <env>` | Write to `env/project/development` or `env/project/production` instead of the shared v3 file |
| `--local` | Write to the machine-local override document under `~/.hush/state/projects/<slug>/user/local-overrides.encrypted` |
| `--file <path-or-alias>` | Write to a specific file: a declared repository path (`env/project/staging`), a repository alias (`shared`, `development`, `production`), or the machine-local store (`local`, `user/local`) |
| `--repo-local` | Shorthand for `--file user/local` — the machine-local store |
| `--gui` | Use a native GUI dialog for input instead of terminal or piped input |
| `--global` | Set the secret in `~/.hush` instead of the current project store |

Supply exactly one destination selector. `--file`, `--repo-local`/`--local`, and `--env` cannot be combined. `hush set` intentionally rejects `--target` before reading a value because a target can contain multiple files; inspect precedence with `hush resolve <target>`, then select the intended file with `--file`.

### Storage Classes

The first segment of a path names where the secret is stored. A selector's meaning never depends on repository state:

| Path | Storage | Committed? | Who can decrypt |
|------|---------|-----------|-----------------|
| `user/**` | Machine-local override store | No — lives under `~/.hush/state/` | Only this machine |
| everything else (`env/**`, `artifacts/**`, …) | Repository file under `.hush/files/` | Yes | Every identity in the file's reader set |

`user/local` is the only machine-local destination, and `user/**` can never be declared as a repository file — `hush file add user/anything` fails, and `copy-key` / `move-key` / `delete-key` reject the namespace outright rather than reinterpreting it.

<Aside type="caution">
`env/project/local` is an ordinary **repository** path — committed, and decryptable by everyone in its reader set. It is no longer an alias for machine-local storage. Writing to it when it is not declared fails with an explicit error instead of silently landing in the machine-local store, and `hush doctor` reports any repository file still named `local`. See the [v7 → v8 migration](/migrations/v7-to-v8/).
</Aside>

### Input Methods (Priority Order)

1. **Inline value**: `hush set KEY "value"` - value provided directly
2. **Piped input**: `echo "value" | hush set KEY` - reads from stdin
3. **GUI dialog**: Opens when `--gui` flag is used
4. **Interactive prompt**: Terminal prompt with visible input

Flags can appear before or after the optional inline value. These are equivalent:

```bash
hush set --global API_KEY "value"
hush set API_KEY "value" --global
```

### How It Works

1. Gets the value from inline arg, pipe, GUI, or prompt
2. Loads the v3 repository and requires an active identity
3. Shows planned destination before writing (e.g., `will write DATABASE_URL -> user/local`)
4. Updates the selected `.hush/files/**.encrypted` document, or the machine-local override doc
5. Writes the YAML document back in place and emits a write audit event
6. Reads the value back from durable storage to verify the write actually persisted
7. Confirms success with destination file and scope

For global mode, Hush binds global writes to `~/.hush/.sops.yaml` explicitly, so running `hush set --global` from inside another repo still uses the global recipient instead of a repo-local `.sops.yaml`.

### Write Verification

`hush set` never prints a success line without first re-reading the value from durable storage, using the same reader the runtime resolution path uses for that scope. If the value is missing or does not match after the write, the command fails loudly:

```
Write verification failed for API_KEY in user/local (machine-local): the value is
missing when read back from durable storage. The write did not persist; do not treat this
secret as saved.
```

A secrets write that reports success but stores nothing is the worst possible failure mode, so this check is unconditional. Error messages never include the secret value.

Separately, if the value persists but the active target's bundle does not select the file it landed in, `hush set` warns that `hush get` will not return it there:

```
warning: API_KEY is stored in env/project/staging, but target "runtime" does not resolve
that file, so "hush get API_KEY" will not return it here. Add env/project/staging to that
target's bundle, or run "hush trace API_KEY" to see which targets select it.
```

This is a warning rather than an error because writing into a file the current target does not resolve is a normal stage-split workflow.

### Conflict Detection

When writing to `shared`, Hush checks if the key already exists in `local`, `development`, or `production`. If a conflict is detected, it warns:

```
will write DATABASE_URL -> env/project/shared
⚠ DATABASE_URL already exists in user/local
```

### Example Output

```
$ hush set DATABASE_URL "postgres://localhost/mydb"
will write DATABASE_URL -> env/project/shared
✓ DATABASE_URL set in env/project/shared (25 chars)

$ hush set API_KEY
Enter value for API_KEY: sk_test_xxx
will write API_KEY -> env/project/shared
✓ API_KEY set in env/project/shared (14 chars)

$ hush set DATABASE_URL "postgres://localhost/mydb" --repo-local
will write DATABASE_URL -> user/local
✓ DATABASE_URL set in user/local (25 chars)
```

### TTY Input

When entering secrets interactively, trailing newlines (`\r`, `\n`) are automatically trimmed to prevent issues with trailing whitespace in secrets.

<Aside type="tip">
AI agents can use inline values directly: `hush set KEY "value"`. For user-provided secrets, use interactive mode: `hush set KEY`.
</Aside>

## copy-key / move-key

Copy or move one key between encrypted v3 file documents without printing the decrypted value. Use this when a secret exists in Hush but belongs in a different service/environment file for target resolution.

```bash
# Copy a shared production key into the API production file
hush copy-key RESEND_API_KEY --from env/project/production --to env/api/production

# Move a key when ownership should change to the destination service file
hush move-key RESEND_API_KEY --from env/project/production --to env/api/production

# JSON metadata only; no values
hush copy-key RESEND_API_KEY --from env/project/production --to env/api/production --json
```

### Options

| Option | Description |
|--------|-------------|
| `--from <file-path>` | Source encrypted v3 file path, such as `env/project/production` |
| `--to <file-path>` | Destination encrypted v3 file path, such as `env/api/production` |
| `--json` | Output action metadata without values |

### How It Works

1. Requires an owner active identity because the command mutates encrypted repository documents
2. Finds exactly one matching leaf key in the source file
3. Writes the same encrypted entry under the destination file path
4. Deletes the source entry only for `move-key`
5. Re-encrypts touched file documents and emits audit metadata

`copy-key` and `move-key` do not edit bundle imports. They are explicit ownership/location changes. If multiple services intentionally share one secret, keep it in a `project-*` file and add explicit bundle imports instead.

## delete-key

Delete one key from an encrypted v3 file document. This is the safe way to remove accidental or unwanted secrets from Hush.

```bash
# Delete a key from shared secrets
hush delete-key OLD_API_KEY --from env/project/shared

# Delete a key with JSON output
hush delete-key OLD_API_KEY --from env/project/shared --json

# Delete without confirmation prompt (for automation)
hush delete-key OLD_API_KEY --from env/project/shared --yes
```

### Options

| Option | Description |
|--------|-------------|
| `--from <file-path>` | Source encrypted v3 file path, such as `env/project/shared` (required) |
| `--yes` | Skip confirmation prompt |
| `--json` | Output action metadata without values |

### How It Works

1. Requires an owner active identity because the command mutates encrypted repository documents
2. Finds exactly one matching leaf key in the specified file
3. Shows preview of what will be deleted
4. Prompts for confirmation (unless `--yes`)
5. Removes the key from the document
6. Re-encrypts the file and emits audit metadata

### Example Output

```
$ hush delete-key OLD_API_KEY --from env/project/shared
This will delete OLD_API_KEY from env/project/shared
Type "yes" to confirm: yes
ok: true
action: delete
key: OLD_API_KEY
from: env/project/shared
logicalPath: env/project/shared/OLD_API_KEY
```

<Aside type="tip">
Use `hush delete-key` instead of manually editing encrypted files. It ensures proper audit trails and prevents accidental corruption.
</Aside>

## edit

Edit a v3 document through a decrypted temporary YAML file in your `$EDITOR`.

```bash
# Edit shared secrets
hush edit

# Edit environment-specific secrets
hush edit development
hush edit production
hush edit dev
hush edit prod

# Edit local overrides
hush edit local

# Edit any file declared in the manifest by its full v3 path
# (see `hush file list` for the registered files)
hush edit env/targets/media/runtime
hush edit env/api/production

# Edit the explicit global store
hush edit --global

# Use a specific editor for this session
hush edit shared --editor vim
hush edit shared --editor "code --wait"

# Use EDITOR environment variable
EDITOR=nano hush edit shared
```

### Options

| Option | Description |
|--------|-------------|
| `--editor <command>` | Override editor for this session (e.g., `vim`, `code --wait`) |
| `--global` | Edit secrets in `~/.hush` instead of the current project store |

### File argument

`hush edit [file]` accepts either a short alias (`shared`, `development`/`dev`, `production`/`prod`,
`local`) or any file declared in the repository manifest, given by its full v3 path
(e.g. `env/targets/media/runtime`). Run `hush file list` to see the registered files. An undeclared
path hard-errors instead of silently falling back to another file.

### How It Works

1. Resolves the target v3 document — a short alias or any declared v3 file path (machine-local for `local`)
2. Decrypts that document to a temporary YAML file
3. Opens the temp file in `$EDITOR` (or `--editor` override), validates it on close, then re-encrypts it back to the `.encrypted` path
4. Logs the resolved editor command for debugging
5. Emits a write audit event

When `--global` is used, the edit flow also binds to `~/.hush/.sops.yaml`, even if the current working directory has its own `.sops.yaml`.

### Editor Resolution

Hush resolves the editor in this order:
1. `--editor` flag (if provided)
2. `EDITOR` environment variable
3. `vi` (default fallback)

<Aside type="tip">
Use `--editor` to override the default editor without changing your environment: `hush edit shared --editor vim`
</Aside>

<Aside type="caution">
Make sure your `$EDITOR` environment variable is set or use `--editor`. For VS Code, use `code --wait` so hush knows when you're done editing.
</Aside>

## bootstrap

Bootstrap a v3 repository rooted at `.hush/`.

```bash
hush bootstrap

# Bootstrap the explicit global store
hush bootstrap --global

# Force a child-local repo even when a parent .hush/ exists
hush bootstrap --new-repo

# Skip interactive confirmation (CI / non-interactive)
hush bootstrap --yes
```

`hush bootstrap` is the canonical setup flow for Task 6. It creates the initial v3 repository layout, `.sops.yaml`, default identities, bundle and target shells, and the machine-local active identity pointer. A fresh bootstrap should leave both `hush status` and `hush inspect` ready to run without extra repair steps.

When run inside a nested git repository, bootstrap walks upward to find an existing parent `.hush/` repository and joins it. Use `--new-repo` to force a child-local repository instead. Use `--yes` (or `-y`) to skip the interactive confirmation prompt in non-interactive mode.

When package metadata does not declare a project identifier, bootstrap falls back to the repo basename (for example `bottown`) instead of inventing a nested `local/<repo>` identity.

### Created layout

```text
.hush/
  manifest.encrypted
  files/
    env/project/shared.encrypted
.sops.yaml
~/.hush/state/projects/<project-slug>/active-identity.json
```

### Default identities and shells

- Identities: `owner-local`, `member-local`, `ci`
- Bundle shell: `project`
- Target shells: `runtime`, `example`
- Initial active identity: `owner-local`

## config

Inspect or update v3 structural config without treating plaintext YAML as the source of truth.

```bash
hush config show
hush config show --json
hush config show identities
hush config active-identity
hush config active-identity member-local
hush config readers env/project/shared --roles owner,member,ci
hush config readers env/project/shared --identities owner-local,ci
```

### Subcommands

| Subcommand | Description |
|-----------|-------------|
| `show [section]` | Show v3 structure. Sections: `manifest`, `identities`, `bundles`, `targets`, `imports`, `files`, `state` |
| `active-identity [name]` | Show the current active identity, or set it when a name is provided |
| `readers <file-path> --roles <csv> --identities <csv>` | Update the file-scoped readers on one encrypted file |

### Notes

- `show` returns structural data only. It does not materialize secret values.
- Add `--json` to `show` for machine-readable structural output. JSON output includes paths, readers, bundles, targets, and state metadata only — never decrypted values.
- `active-identity` writes machine-local state under `~/.hush/state/projects/<project-slug>/active-identity.json`.
- `readers` updates one ACL unit at a time, because files are the only ACL boundary in v3.

## Topology Management

Files, bundles, and targets form a three-layer hierarchy. Build from the bottom up and tear down from the top.

```text
Files  →  Bundles  →  Targets
```

- **Files** are the encrypted documents that hold secret entries. Each file has its own ACL (readers).
- **Bundles** package one or more file references together. A bundle is the unit of access for a target.
- **Targets** consume a bundle and declare how secrets are materialized (format, mode, filename).

All topology mutations require the **owner role**. Reference validation runs before any disk write, so dangling refs are rejected before encryption.

### Lifecycle example

```bash
# 1. Create an encrypted file
hush file add env/api/production --roles owner,ci

# 2. Create a bundle that references it
hush bundle add api-production --files env/api/production

# 3. Create a target that consumes the bundle
hush target add api-production --bundle api-production --format dotenv

# 4. Verify the target resolves
hush verify-target api-production --require DATABASE_URL

# 5. Teardown in reverse order
hush target remove api-production
hush bundle remove api-production
hush file remove env/api/production
```

## file

Manage encrypted file documents in the v3 repository.

```bash
# Add a new encrypted file
hush file add env/api/production --roles owner,ci
hush file add env/api/staging --roles owner,member,ci
hush file add env/project/shared --identities owner-local,ci

# Update readers on an existing file
hush file readers env/api/production --roles owner,ci
hush file readers env/api/production --identities owner-local,ci

# List all files
hush file list
hush file list --json

# Remove a file
hush file remove env/api/staging
hush file remove env/api/production --keep-file
```

### Subcommands

| Subcommand | Description |
|-----------|-------------|
| `add <namespaced-path>` | Create a new encrypted file document with the given readers |
| `remove <namespaced-path>` | Remove a file from the manifest and delete the encrypted disk file |
| `list` | List all encrypted files with their readers |
| `readers <namespaced-path>` | Update the ACL readers on an existing file |

### Options for `file add` and `file readers`

| Option | Description |
|--------|-------------|
| `--roles <csv>` | Comma-separated roles: `owner`, `member`, `ci` |
| `--identities <csv>` | Comma-separated identity names |

### Options for `file remove`

| Option | Description |
|--------|-------------|
| `--keep-file` | Remove only the manifest entry; leave the encrypted disk file in place |

### Safety semantics

- Requires the owner role. Non-owner identities cannot add, remove, or update files.
- `file remove` fails if the file is still referenced by any bundle. Remove the bundle first.
- All mutations emit `metadata_change` audit events.

<Aside type="tip">
Use `hush file readers` to grant CI access to a file without recreating it. This is the safe way to expand or restrict who can decrypt a file.
</Aside>

## bundle

Manage bundles of encrypted file references.

```bash
# Create a bundle from explicit file refs
hush bundle add api-production --files env/api/production
hush bundle add api-production --files env/api/production,env/project/shared

# Add or remove a file from an existing bundle
hush bundle add-file api-production env/project/shared
hush bundle remove-file api-production env/project/shared

# List all bundles
hush bundle list
hush bundle list --json

# Remove a bundle
hush bundle remove api-production
```

### Subcommands

| Subcommand | Description |
|-----------|-------------|
| `add <name>` | Create a new bundle, optionally with an initial file list |
| `add-file <bundle> <file>` | Add a file reference to an existing bundle |
| `remove-file <bundle> <file>` | Remove a file reference from a bundle |
| `remove <name>` | Remove a bundle from the manifest |
| `list` | List all bundles with their file references |

### Options for `bundle add`

| Option | Description |
|--------|-------------|
| `--files <csv>` | Comma-separated namespaced file paths to include in the bundle |

### Safety semantics

- Requires the owner role. All bundle mutations emit `metadata_change` audit events.
- `bundle add` validates that every file path exists in the file index before writing.
- Duplicate file refs in `--files` are rejected.
- `bundle remove` fails if the bundle is still referenced by any target. Remove the target first.

<Aside type="tip">
Use `hush bundle add-file` and `hush bundle remove-file` to incrementally adjust what a bundle includes without recreating it.
</Aside>

## target

Manage targets in the v3 repository.

```bash
# Add a target
hush target add api-production --bundle api-production --format dotenv
hush target add ios-signing --bundle ios-signing --format json --mode file
hush target add web-example --bundle web --format dotenv --mode example

# List all targets
hush target list
hush target list --json

# Remove a target
hush target remove api-production
```

## push

Push resolved v3 target output to configured remote runtimes.

```bash
# Push all configured targets
hush push

# Push a specific configured target
hush push -t api
hush push -t app

# Preview without pushing
hush push --dry-run

# Detailed preview showing each variable
hush push --dry-run --verbose
hush push -t app --dry-run --verbose

# Ad-hoc Vercel projection
hush push --vercel -t web --project prj_123 --environment production --dry-run

# Stage-scoped Cloudflare Workers push (passes --env <name> to wrangler secret put)
hush push -t worker --wrangler-env staging --dry-run
hush push -t worker --wrangler-env production
```

### Options

| Option | Description |
|--------|-------------|
| `-t, --target <name>` | Push only the specified target |
| `--dry-run` | Preview what would be pushed without making changes |
| `--verbose` | Show detailed output (with `--dry-run`) |
| `--vercel` | Treat the selected target as a Vercel projection and call the Vercel REST API directly |
| `--project <id>` | Override the Vercel project id (`push_to.projectId` or explicit ad-hoc mode) |
| `--team <id>` | Optional Vercel team id for scoped project access |
| `--environment <name>` | Vercel environment target (`production`, `preview`, `development`); repeat to target more than one |
| `--wrangler-env <name>` | Wrangler environment name passed as `--env` to each `wrangler secret put` call; enables staging vs production stage routing for Cloudflare Workers targets |

### Supported Destinations

| Target Type | Configuration | Transport |
|-------------|---------------|-----------|
| **Cloudflare Workers** | `format: wrangler` | `wrangler secret put` |
| **Cloudflare Pages** | `push_to.type: cloudflare-pages` | `wrangler pages secret put` |
| **Vercel** | `push_to.type: vercel` or `format: vercel` | `POST /v10/projects/{projectId}/env?upsert=true` |

### Configuration Examples

**Cloudflare Workers (automatic with `format: wrangler`):**
```yaml
targets:
  api:
    bundle: api-runtime
    format: wrangler
```

**Vercel (migrated legacy `push_to.type: vercel` metadata):**
```yaml
targets:
  web:
    bundle: web-runtime
    format: vercel
    push_to:
      type: vercel
      projectId: prj_123
      teamId: team_456
      environments: [production, preview]
```

Today the structured `push_to` metadata comes from migrated legacy config. In a pure v3 repo without that metadata, use `format: vercel` plus the explicit CLI flags (`--project`, `--team`, `--environment`) for ad-hoc projection.

### How It Works

1. Loads the v3 repository and selects configured push targets, or a single explicit `--vercel` target
2. Resolves the target env through the shared runtime pipeline and emits audit-safe read/materialize events
3. For Cloudflare targets, pushes each resolved env var through `wrangler`
4. For Vercel targets, maps each env key to `sensitive` or `encrypted` and upserts it through the Vercel REST API

<Aside type="note">
Cloudflare push requires the `wrangler` CLI to be installed and authenticated. Vercel push requires a `VERCEL_TOKEN`, either in `push_to.token`, the resolved Hush target, or the parent process environment.
</Aside>

<Aside type="tip">
Use `hush push -t <target> --dry-run --verbose` to preview exactly what Hush would send to a configured target, or `hush push --vercel ... --dry-run` for ad-hoc Vercel projection.
</Aside>

## project

Reconcile a repo-owned project environment contract against a Hush target, local `wrangler.toml` vars, remote Worker secret metadata, and provider validators such as Resend.

```bash
# Show current drift without failing the shell
hush project plan staging

# Fail CI if Hush target or provider checks drift
hush project validate staging --skip-remote

# Push runtime Worker secrets from Hush to Cloudflare
hush project sync staging

# Pick an explicit config or surface when auto-discovery is not enough
hush project validate production --config packages/runtime-config/config/hush-project-env.json --surface api-worker
```

### Subcommands

| Subcommand | Behavior |
|------------|----------|
| `plan` | Report contract drift and planned sync actions without failing |
| `validate` | Evaluate and exit non-zero when drift remains |
| `sync` | Push declared runtime Worker secrets from the selected Hush target and exit non-zero when drift remains |

### Options

| Option | Description |
|--------|-------------|
| `--config <path>` | Explicit project config path. If omitted, Hush auto-discovers `hush-project-env.json`, `.hush/project-env.json`, `config/hush-project-env.json`, or `packages/runtime-config/config/hush-project-env.json` |
| `--surface <name>` | Named surface inside the project config (default: first surface, commonly `api-worker`) |
| `--skip-remote` | Skip Cloudflare Worker secret metadata checks |
| `--skip-provider` | Skip provider validators such as Resend |
| `--dry-run` | For `sync`, report what would be pushed without calling Wrangler |
| `--json` | Emit machine-readable status payload |

### Contract Shape

The project config points at two repo-owned JSON documents:

- `runtime-requirements.json` declares secret vs variable delivery and required stages
- `environment-targets.json` declares derived non-secret values such as URLs or allowed origins

The selected surface then maps that contract onto:

- a Hush target name per stage
- a `wrangler.toml` directory and optional Wrangler env
- deploy-only secrets that must still resolve in Hush
- optional provider validators

### How It Works

1. Loads the project config and resolves the selected stage + surface
2. Resolves the configured Hush target through the same v3 runtime path used by `hush run`
3. Verifies required target-visible keys exist without printing values
4. Compares declared runtime variables against `wrangler.toml`
5. Optionally checks remote Worker secret names with Wrangler
6. Optionally validates provider keys such as `RESEND_API_KEY`
7. For `sync`, pushes runtime secret values with `wrangler secret put`

<Aside type="tip">
Use `hush project validate <stage> --skip-remote` early in CI, then run `hush project sync <stage>` immediately before the Worker deploy step.
</Aside>

## verify-target

Verify that a v3 target resolves and contains required keys. **Use this in release automation before syncing remote runtime secrets or flipping traffic.**

```bash
# Verify the target resolves at all
hush verify-target api-production

# Require specific runtime keys
hush verify-target api-production --require JWT_SECRET --require RESEND_API_KEY

# JSON output for CI or agents
hush verify-target api-production --require RESEND_API_KEY --json
```

### Options

| Option | Description |
|--------|-------------|
| `--require <key>` | Require a leaf key to resolve from the selected target bundle. Repeatable. |
| `--json` | Output machine-readable verification results without values |

### How It Works

1. Loads the v3 repository and active identity
2. Resolves the named target with the same resolver used by `run`, `push`, and `materialize`
3. Checks file ACLs, conflicts, and required leaf keys
4. Prints only paths, key names, files, bundles, and errors — never decrypted values

### Service × environment topology guidance

For monorepos, model concrete consumer surfaces as `service-environment` bundles/targets:

```text
api-development
api-staging
api-production
root-development
root-staging
root-production
```

Use `project-*` only for intentionally shared material:

```text
project-shared
project-development
project-staging
project-production
```

Files remain the security boundary, bundles package files, and targets consume bundles. A target such as `api-production` should not see `project-production` secrets unless its bundle explicitly imports that shared bundle/file or the key is copied/moved into an API-owned file. This keeps production secret flow visible and agent-safe.

## decrypt --force (Last Resort)

<Aside type="danger">
This command writes persisted plaintext artifacts to disk. Use `hush run` instead whenever possible.
</Aside>

<Aside type="tip">
If you need a maintained file-based workflow, prefer `hush materialize` over `decrypt --force`. `materialize` supports explicit output roots, JSON metadata, and bundle-oriented artifact handling.
</Aside>

Write decrypted targets to `.hush-materialized/` as persisted plaintext artifacts. **Requires `--force` flag and interactive confirmation.**

```bash
hush decrypt --force
hush decrypt --force -e production
```

### Why This Exists

Some edge cases genuinely require persisted plaintext artifacts:
- Docker or packaging workflows that cannot inherit process env directly
- Legacy tooling that can only read files on disk
- Temporary break-glass debugging of target output

### Safety Features

1. **Requires `--force` flag** - Won't run without explicit opt-in
2. **Interactive confirmation** - Must type `yes` to proceed
3. **Writes under `.hush-materialized/`** - Plaintext is isolated to one explicit directory
4. **Shared materialization audit** - Uses the same audited runtime flow as `hush run`

### How It Works

1. Loads the v3 repository and selects all non-example targets
2. Materializes each target through the shared runtime pipeline in persisted mode
3. Writes target artifacts under `.hush-materialized/targets/` and related artifact paths
4. Leaves the files on disk until you delete them explicitly

<Aside type="tip">
After using `decrypt --force`, delete the persisted output directory when done:
```bash
rm -rf .hush-materialized
```
Or better yet, switch to `hush run -- <command>` for future use.
</Aside>

## list

List variable names. Values are **masked by default**. Use `--reveal` to print plaintext values.

```bash
hush list
hush list --reveal
hush list -e production
```

### Options

| Option | Description |
|--------|-------------|
| `--reveal` | Print plaintext values instead of masked output |

<Aside type="caution">
`--reveal` prints actual secret values to the terminal. Use `hush inspect` for AI-safe output that never reveals values.
</Aside>

## Troubleshooting

### "no identity matched any of the recipients"

This error means SOPS cannot find your decryption key.

**Most common cause:** direnv not loaded.

Hush stores per-project keys at `~/.config/sops/age/keys/{project}.txt`. Hush now auto-matches those files against the `.sops.yaml` recipient for normal CLI commands, so a fresh `hush bootstrap` works even if `package.json.repository` is missing. `SOPS_AGE_KEY_FILE` is still the best explicit override when you need to force a specific key file.

```bash
# 1. Verify direnv is installed and hooked
brew install direnv
echo 'eval "$(direnv hook zsh)"' >> ~/.zshrc  # or bash
source ~/.zshrc

# 2. Allow direnv in the project
cd /path/to/project
direnv allow

# 3. Verify the env var when you want an explicit override
echo $SOPS_AGE_KEY_FILE
# Optional, but if set it should output: /Users/you/.config/sops/age/keys/project-name.txt

# 4. Test
hush status
hush inspect
```

### "age key not found"

The key file doesn't exist at the expected location.

```bash
# Check where hush expects the key
hush status   # Look at "Local key:" line

# Get the key from a team member and save it manually
# Save to the path shown in hush status, then run:
hush keys setup
```

If the key was stored as `SOPS_AGE_KEY` in a Vercel project, recover it in one command:

```bash
# Requires VERCEL_TOKEN in env or --token flag
hush keys pull --from vercel --project prj_123
hush keys pull --from vercel --project prj_123 --team team_abc
hush keys pull --from vercel --project prj_123 --force  # overwrite existing local key

# Confirm recovery
hush doctor
hush inspect
```

`keys pull --from vercel` fetches `SOPS_AGE_KEY` via the Vercel REST API (with `decrypt=true`), validates the
value is an age private key, derives the public key safely, and writes to
`~/.config/sops/age/keys/{project}.txt`. Private key values are never printed to output.

### Key exists but wrong project

If you have a key but it's for a different project:

```bash
# List all local keys
hush keys list

# Copy the correct key into the expected local path, then verify it
hush keys setup
```

### "SOPS is not installed"

```bash
brew install sops age   # macOS
# See Getting Started for Linux/Windows
```

### direnv not loading automatically

Make sure you've added the direnv hook to your shell:

```bash
# For zsh (~/.zshrc)
eval "$(direnv hook zsh)"

# For bash (~/.bashrc)
eval "$(direnv hook bash)"
```

Then reload your shell or open a new terminal.
