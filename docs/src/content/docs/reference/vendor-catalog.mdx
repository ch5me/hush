Hush stores vendor credentials as encrypted entries in your repository. This catalog documents the typical secrets each vendor requires and how to structure them in Hush.

## GitHub OAuth App

A [GitHub OAuth App](https://docs.github.com/en/apps/oauth-apps) authenticates users via OAuth 2.0. Use this when your app acts on behalf of a user — reading repositories, posting commits, managing Gists.

### Typical Secrets

| Key | Description | Sensitive |
|-----|-------------|-----------|
| `GITHUB_CLIENT_ID` | OAuth app client ID from GitHub App settings | no |
| `GITHUB_CLIENT_SECRET` | OAuth app client secret from GitHub App settings | yes |

### Setup

1. Create a GitHub OAuth App at [github.com/settings/applications/new](https://github.com/settings/applications/new)
2. Set the homepage URL and authorization callback URL
3. Note the **Client ID** and generate a **Client Secret**
4. Store the secrets in Hush:

```bash
hush file add env/integrations/github-oauth --roles owner
hush set GITHUB_CLIENT_ID --from-value "your-client-id"
hush set GITHUB_CLIENT_SECRET --from-value "your-client-secret"
```

### File Layout

```
.hush/files/
  env/integrations/github-oauth.encrypted
```

### Bundle and Target

```bash
hush bundle add github-oauth-bundle --files env/integrations/github-oauth
hush target add github-oauth-runtime --bundle github-oauth-bundle --format dotenv
```

<Aside type="tip">
The OAuth flow requires an exact redirect URI match. Verify the callback URL in your GitHub OAuth App settings matches your app's redirect endpoint exactly.
</Aside>

### Notes

- OAuth tokens expire; implement token refresh if persisting tokens
- OAuth Apps are tied to a user account — for org-owned apps, use a GitHub App instead
- [GitHub OAuth App docs](https://docs.github.com/en/apps/oauth-apps)

## Google OAuth 2.0

A [Google OAuth 2.0](https://developers.google.com/identity/protocols/oauth2) app authenticates users via Google's OAuth flow. Use this when your app acts on behalf of a user — accessing Google Drive, Gmail, Calendar, YouTube, or any Google API.

### Typical Secrets

| Key | Description | Sensitive |
|-----|-------------|-----------|
| `GOOGLE_CLIENT_ID` | OAuth 2.0 client ID from Google Cloud Console | no |
| `GOOGLE_CLIENT_SECRET` | OAuth 2.0 client secret from Google Cloud Console | yes |

### Setup

1. Go to the [Google Cloud Console](https://console.cloud.google.com) and create or select a project
2. Navigate to **APIs & Services** → **Credentials** → **Create Credentials** → **OAuth client ID**
3. Set application type to **Web application** and add your redirect URI(s)
4. Note the **Client ID** and **Client Secret**
5. Configure the **OAuth consent screen** — add scopes for the Google APIs you need (e.g., `https://www.googleapis.com/auth/drive.readonly`)
6. Store the secrets in Hush:

```bash
hush file add env/integrations/google-oauth --roles owner
hush set GOOGLE_CLIENT_ID --from-value "your-client-id.apps.googleusercontent.com"
hush set GOOGLE_CLIENT_SECRET --from-value "your-client-secret"
```

### File Layout

```
.hush/files/
  env/integrations/google-oauth.encrypted
```

### Bundle and Target

```bash
hush bundle add google-oauth-bundle --files env/integrations/google-oauth
hush target add google-oauth-runtime --bundle google-oauth-bundle --format dotenv
```

### OAuth Flow

Redirect the user to Google's consent screen, then exchange the authorization code for tokens:

```typescript
// Build the authorization URL
const authUrl = new URL('https://accounts.google.com/o/oauth2/v2/auth');
authUrl.searchParams.set('client_id', process.env.GOOGLE_CLIENT_ID);
authUrl.searchParams.set('redirect_uri', 'https://yourapp.com/oauth/callback');
authUrl.searchParams.set('response_type', 'code');
authUrl.searchParams.set('scope', 'https://www.googleapis.com/auth/drive.readonly');
authUrl.searchParams.set('access_type', 'offline'); // enables refresh tokens
authUrl.searchParams.set('prompt', 'consent'); // forces refresh token issuance

// Exchange code for tokens
const tokenResponse = await fetch('https://oauth2.googleapis.com/token', {
  method: 'POST',
  headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
  body: new URLSearchParams({
    code: authCode,
    client_id: process.env.GOOGLE_CLIENT_ID,
    client_secret: process.env.GOOGLE_CLIENT_SECRET,
    redirect_uri: 'https://yourapp.com/oauth/callback',
    grant_type: 'authorization_code',
  }),
});
const { access_token, refresh_token, expires_in } = await tokenResponse.json();
```

<Aside type="tip">
Include `access_type=offline` in your authorization request to receive a refresh token. Refresh tokens allow your app to obtain new access tokens without requiring the user to re-authenticate.
</Aside>

<Aside type="caution">
Google may stop issuing refresh tokens after 6 months of inactivity. Your app should handle `invalid_grant` errors gracefully and redirect the user to re-consent if needed.
</Aside>

### Notes

- Redirect URIs must match exactly — wildcards are not supported
- Production apps must complete Google's **OAuth verification** to remove the "unverified app" banner and lift the 100-user cap
- Adding new scopes may require re-submitting for verification
- [Google OAuth 2.0 docs](https://developers.google.com/identity/protocols/oauth2)
- [Google OAuth Scopes](https://developers.google.com/identity/protocols/oauth2/scopes)

## GitHub App

A [GitHub App](https://docs.github.com/en/apps/creating-github-apps) is an entity installed on orgs or user accounts. GitHub Apps can also use OAuth 2.0 for user-to-server requests. Use this for bot-style access, webhook receivers, or granular org-scoped permissions.

### Typical Secrets

| Key | Description | Sensitive |
|-----|-------------|-----------|
| `GITHUB_APP_ID` | GitHub App's numeric ID | no |
| `GITHUB_APP_PRIVATE_KEY` | Private key (.pem) for signing JWTs | yes |
| `GITHUB_APP_CLIENT_ID` | OAuth client ID for user-to-server requests | no |
| `GITHUB_APP_CLIENT_SECRET` | OAuth client secret for user-to-server requests | yes |
| `GITHUB_WEBHOOK_SECRET` | Shared secret for validating webhook payloads | yes |

### Setup

1. Create a GitHub App at [github.com/settings/apps/new](https://github.com/settings/apps/new)
2. Set the app name, homepage URL, and enable the webhook
3. Generate a **private key** — downloads as `.pem`. Store immediately in Hush:

```bash
hush file add env/integrations/github-app --roles owner
hush set GITHUB_APP_ID --from-value "123456"
hush set GITHUB_APP_PRIVATE_KEY --from-value "$(cat /path/to/app.private-key.pem)"
hush set GITHUB_APP_CLIENT_ID --from-value "Iv1.abc123..."
hush set GITHUB_APP_CLIENT_SECRET --from-value "ov2.xxx..."
hush set GITHUB_WEBHOOK_SECRET --from-value "your-webhook-secret"
```

4. Install the app on your org or user account and note the **Installation ID**

### File Layout

```
.hush/files/
  env/integrations/github-app.encrypted
```

### Bundle and Target

```bash
hush bundle add github-app-bundle --files env/integrations/github-app
hush target add github-app-runtime --bundle github-app-bundle --format dotenv
```

### Authenticate as App (JWT)

GitHub Apps use short-lived JWTs signed with the private key:

```typescript
import { signJwt } from './jwt'; // your JWT library

const jwt = await signJwt({
  iss: process.env.GITHUB_APP_ID,
  exp: Math.floor(Date.now() / 1000) + 600,
}, process.env.GITHUB_APP_PRIVATE_KEY, 'RS256');

const installationResponse = await fetch(
  `https://api.github.com/app/installations/${INSTALLATION_ID}/access_tokens`,
  {
    headers: {
      Authorization: `Bearer ${jwt}`,
      Accept: 'application/vnd.github+json',
    },
  }
);
const { token } = await installationResponse.json();
// Use token for API calls
```

### Authenticate as User (OAuth)

GitHub Apps can also use OAuth for user-to-server requests:

```typescript
const response = await fetch('https://github.com/login/oauth/access_token', {
  method: 'POST',
  headers: { Accept: 'application/json', 'Content-Type': 'application/json' },
  body: JSON.stringify({
    client_id: process.env.GITHUB_APP_CLIENT_ID,
    client_secret: process.env.GITHUB_APP_CLIENT_SECRET,
    code: oauthCode,
  }),
});
const { access_token } = await response.json();
```

### Validate Webhooks

```typescript
import { createHmac } from 'crypto';

export function validateWebhook(
  payload: Buffer,
  signature: string,
  secret: string
): boolean {
  const expected = createHmac('sha256', secret)
    .update(payload)
    .digest('hex');
  return `sha256=${expected}` === signature;
}
```

<Aside type="caution">
Private keys cannot be retrieved after generation. Download and store in Hush immediately when creating a GitHub App.
</Aside>

### Notes

- App tokens expire after 1 hour — refresh using the installation token flow
- Webhook secrets are optional but strongly recommended
- GitHub App permissions are granted at install time per org/repo
- [GitHub App docs](https://docs.github.com/en/apps/creating-github-apps)
- [App authentication](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app)
- [OAuth with GitHub Apps](https://docs.github.com/en/apps/creating-github-apps/building-oauth-apps/authorizing-oauth-apps)

## Stripe

[Stripe](https://stripe.com) is a payment processing platform. Use Stripe API keys for server-side payments, billing, and webhook receivers. For apps acting on behalf of connected merchants, use Stripe Connect OAuth.

### Typical Secrets

| Key | Description | Sensitive |
|-----|-------------|-----------|
| `STRIPE_SECRET_KEY` | Secret API key from Stripe dashboard | yes |
| `STRIPE_PUBLISHABLE_KEY` | Publishable API key (often public) | no |
| `STRIPE_WEBHOOK_SECRET` | Webhook signing secret for validating payloads | yes |

### Setup

1. Create a Stripe account at [dashboard.stripe.com](https://dashboard.stripe.com)
2. Navigate to **Developers** → **API keys**
3. Copy the **Secret key** (`sk_live_...` or `sk_test_...`) — store immediately in Hush
4. Copy the **Publishable key** (`pk_live_...` or `pk_test_...`) — non-sensitive
5. For webhooks, navigate to **Developers** → **Webhooks** and add an endpoint
6. Copy the **Webhook signing secret** (`whsec_...`) — store in Hush

Store the secrets in Hush:

```bash
hush file add env/vendor/stripe --roles owner
hush set STRIPE_SECRET_KEY --from-value "sk_live_..."
hush set STRIPE_PUBLISHABLE_KEY --from-value "pk_live_..."
hush set STRIPE_WEBHOOK_SECRET --from-value "whsec_..."
```

### File Layout

```
.hush/files/
  env/vendor/stripe.encrypted
```

### Bundle and Target

```bash
hush bundle add stripe-bundle --files env/vendor/stripe
hush target add stripe-runtime --bundle stripe-bundle --format dotenv
```

### Validate Webhooks

Stripe signs webhook payloads using `stripe-signature` header:

```typescript
import Stripe from 'stripe';

const stripe = new Stripe(process.env.STRIPE_SECRET_KEY, {
  apiVersion: '2024-06-20',
});

export async function validateStripeWebhook(
  payload: Buffer,
  signature: string,
  secret: string
): Promise<boolean> {
  try {
    stripe.webhooks.constructEvent(payload, signature, secret);
    return true;
  } catch {
    return false;
  }
}
```

<Aside type="tip">
Use the `stripe` Node.js SDK's built-in `constructEvent` for webhook validation — it handles timing attacks and replay attacks automatically.
</Aside>

### Notes

- Secret keys cannot be retrieved after creation — store immediately
- Use test keys (`sk_test_...`) during development
- Stripe Connect OAuth is available for platforms acting on behalf of merchants
- [Stripe API docs](https://stripe.com/docs/api)
- [Stripe webhook docs](https://stripe.com/docs/webhooks)

## Sign in with Apple

[Sign in with Apple](https://developer.apple.com/documentation/sign_in_with_apple) provides authentication for apps on Apple platforms and the web. It uses a provider-based OAuth 2.0 flow with JWT tokens for backend verification.

### Typical Secrets

| Key | Description | Sensitive |
|-----|-------------|-----------|
| `APPLE_CLIENT_ID` | Apple **Services ID** identifier (not the same as the bundle ID) | no |
| `APPLE_TEAM_ID` | Apple Developer Team ID from the membership page | no |
| `APPLE_KEY_ID` | Key ID of the Sign in with Apple private key | no |
| `APPLE_PRIVATE_KEY` | Private key (.p8) for signing and verifying tokens | yes |
| `APPLE_APP_BUNDLE_IDENTIFIER` | Native iOS bundle identifier (optional, distinct from Client ID) | no |

### Critical: Client ID vs Bundle Identifier

For Sign in with Apple, `APPLE_CLIENT_ID` is the **Services ID**, not the iOS bundle identifier. Setting them to the same value causes native Apple Sign In to succeed but server-side token verification to fail with a 401.

Example:

- `APPLE_CLIENT_ID=com.example.servicesid` (Services ID)
- `APPLE_APP_BUNDLE_IDENTIFIER=com.example.app` (iOS bundle ID)

### Setup

1. Create a Sign in with Apple App ID in [Apple Developer Console](https://developer.apple.com)
2. Create a Services ID and enable Sign in with Apple
3. Create a Sign in with Apple key (`.p8`) and note the Key ID
4. Note your Team ID from the membership page
5. Store the secrets in Hush:

```bash
hush file add env/vendor/apple-sign-in --roles owner
hush set APPLE_CLIENT_ID --from-value "com.example.servicesid"
hush set APPLE_TEAM_ID --from-value "TEAM123456"
hush set APPLE_KEY_ID --from-value "KEY123ABC"
hush set APPLE_PRIVATE_KEY --from-value "$(cat /path/to/AuthKey_KEY123ABC.p8)"
hush set APPLE_APP_BUNDLE_IDENTIFIER --from-value "com.example.bundleid"
```

### File Layout

```
.hush/files/
  env/vendor/apple-sign-in.encrypted
```

### Bundle and Target

```bash
hush bundle add apple-sign-in-bundle --files env/vendor/apple-sign-in
hush target add apple-sign-in-runtime --bundle apple-sign-in-bundle --format dotenv
```

Preferred runtime targets:

- `api-dev`
- `api-staging`
- `api-production`

### Native vs Web Flow

For native apps using Better Auth or similar, the client forwards Apple's `authorizationCode` along with the `identityToken`. Ensure the backend receives `authorizationCode` as `accessToken` when calling `authClient.signIn.social({ provider: 'apple', idToken: ... })`.

### Notes

- Sign in with Apple private keys cannot be retrieved after creation — download and store in Hush immediately
- Production can use a dedicated auth key separate from staging
- Do not confuse App Store Connect `.p8` signing keys with Sign in with Apple `.p8` auth keys — they are different workflows
- [Sign in with Apple docs](https://developer.apple.com/documentation/sign_in_with_apple)
- [Sign in with Apple API reference](https://developer.apple.com/documentation/sign_in_with_apple/rest-api)

## Adding a New Vendor

To add a vendor to your Hush repository:

### 1. Create the vendor file

```bash
hush file add env/vendor/<vendor-name> --roles owner
```

### 2. Add secrets

```bash
hush set VENDOR_API_KEY --from-value "your-api-key"
```

### 3. Bundle and target

```bash
hush bundle add <vendor>-bundle --files env/vendor/<vendor-name>
hush target add <vendor>-runtime --bundle <vendor>-bundle --format dotenv
```

### 4. Verify

```bash
hush verify-target <vendor>-runtime --require VENDOR_API_KEY
```

For agent-facing reference, see the [Vendor Catalog wiki topic](../../.llm/wiki/topics/vendor-catalog.md).
